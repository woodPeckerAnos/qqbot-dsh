# 主动介入会话能力 —— 架构方案

> 状态：**架构设计，未实施**。本文件回答一个问题：把主动介入拆成业务方给出的
> 5 种场景、且「同时命中多个时按加载顺序取第一个」之后，最有可能的落地架构
> 是什么。
>
> 与既有文档的关系：
> - [TOPIC-INTERVENTION-PLAN.md](TOPIC-INTERVENTION-PLAN.md)（下称「P0 方案」）
>   是**已实现**的旁听 / 续聊 / 插话底座（Phase 0/1/2，落在分支
>   `feat/topic-intervention-p0`，本分支尚未合并）；
> - 本文件是它的**上层修订**：不推翻规则文件夹 × 拦截器链，而是把
>   「该不该说话」这唯一一次 LLM 判定，从**一个笼统的必要条件**升级为
>   **场景化的单次仲裁**；
> - 未特别标注的现状描述均以 `feat/topic-intervention-p0` 为准（main 上还没有
>   `src/intervention/`）。

## 0. 结论先行（TL;DR）

1. **5 个场景不是并列的 5 条分支，而是落在 3 个不同平面上的判据**
   （触发平面 / 语义平面 / 兜底平面）。把它们当成同层的 `if/else` 去写，
   一定会同时踩两个坑：要么在每条消息上跑 5 次 LLM（成本爆炸），要么用
   同一套阈值伺候 5 种风险完全不同的情形（误报爆炸）。
2. **「按加载顺序取第一个」只在语义平面成立**：一次 LLM 调用接收
   **有序**的场景清单，输出唯一命中场景 ID 与理由；多场景同时成立时，
   由 prompt 里的顺序 + 请求侧的稳定排序共同保证「取第一个」是确定性的，
   且可测（离线回放能复现）。
3. **场景优先级只决定「谁先被听到」，绝不决定「能不能说」**：硬限流、
   焦点预算、准入 try、谷时段这些防刷屏闸门对所有场景一律生效。
   优先级不是免死金牌，否则场景 1（用户 @ 过）会成为刷屏后门。
   （生态侧有个更优雅的第三条路：用**按场景置信度加权的分位数预算**让高优先
   场景自然突破而不开后门，见 §13.2——但那要等 S4 有回放数据之后。）
4. **最有可能的架构 = 三段式**：
   `① 触发（多平面、按场景绑定时机） → ② 仲裁（单次 LLM，场景标签 + 是否发言） → ③ 硬约束（确定性否决链）`。
   其中 ② 就是把现有 `20-semantic-gate` 从「要不要说话」升级为
   「是哪个场景 + 要不要说话」，**输出契约向后兼容**（多一个字段，旧解析器不炸）。
5. **成本纪律只有一条**：一次评估最多一次 LLM 调用；场景判定与发言判定
   **合并**在同一次调用里（多分类 + 决策），不做两段式。
6. 真正的新增工程不在「分类」，而在**话题维度的状态**：
   话题指纹 / 未答问题台账 / 介入记账。没有这三样，场景 2、3、5 无法与
   「已答过」「已插过」「同一话题反复插」区分开，场景 3 尤其会退化成
   「只要有人提问就抢答」。
7. **状态绝不按场景分账**（§3.0）：防刷屏要回答的是「这个群最近说了多少话」，
   是跨场景问题；分场景记账会让每个场景都在自己的额度内合规、合起来仍然刷屏。
   场景只出现在**仲裁的输入输出**与**trace / 指标**里。
8. 两个必须先补的输入缺口，否则场景 1 从根上判不对：
   **bot 自己的上一句不在转录里**（§3.6），**「问题是否已被回答」是本地
   关键词启发式**（§1.2）。现状与硬缺口清单见 §12（独立审计，带行号证据）。

本方案给出的场景编号（供维护者拍板，见 §11）：

```
scene-4 指代      → scene-1 续聊追问 → scene-3 无人应答 → scene-2 持续讨论 → scene-5 兴趣/性格
（被点到名字最优先）  （刚聊过的延续）    （时效最紧）        （最需克制）      （最宽松、最容易饿死）
```

## 1. 五个场景的架构翻译

把业务语言逐条翻译成架构语言时，必须回答四件事：
**时机（什么时候判）／预筛（本地能不能先挡掉）／判据（LLM 要什么证据）／
风险（误报的代价是什么）**。这张表就是整个方案的骨架。

| # | 业务场景 | 触发平面（时机） | 本地预筛 | LLM 需要的证据 | 误报代价 | 对应现有机制 |
|---|---|---|---|---|---|---|
| 1 | @ 之后同话题追问 / 延伸（同人或他人） | **会话事件**：bot 参与过该话题后的窗口内，任何新消息 | 窗口（时间 + 条数）+ 话题连续（指纹相似度） | 与 bot 上一条发言的关系、是否已有他人作答 | 中（回复错人显得笨） | `40-promotion-window`（**已有，但窗口键是「会话 × 发送者」——只覆盖提问者自己的追问，「其他人追问」是缺口**） |
| 2 | 用户之间持续讨论，bot 能提供能力 / 有可答问题 / 有事实性错误 | **话题滚动**：每 N 条消息或 M 分钟收敛一次，不是每条消息判 | 话题活跃度阈值（≥K 条 / ≥2 人 / 无 bot 参与） | 话题摘要 + 最近若干条原文 + 能力清单 | 高（打断人类对话是最大反感源） | `13-sampling-debounce`（采样 + 去抖，**已有骨架，缺话题维度**） |
| 3 | 问题长期无人回答 | **问题台账 + 定时器**：问句挂起 → 答案窗口到期 → 重入评估 | 问句识别（`10-strong-open-question`） + 「是否已被响应」的**语义**判定 | 挂起时长、是否已被回答、问题是否在 bot 能力域内 | 中高（抢答人类正在打字的问题） | `10-strong-open-question`（**已有 defer 与答案窗口，但应答判定是「窗口内有他人发言」的弱启发式，需改为台账 + 仲裁复核**） |
| 4 | 无 @ 但在谈论与 bot 相关的话题（指代） | **会话事件**：每条消息都查（本地几乎零成本） | 别名表命中（精确别名高召回；泛称「机器人/bot」需配合动作词） | 是「对 bot 说」还是「在说 bot 的闲话」（如「这机器人是不是坏了」） | 中（抢话；但答对了体验极好） | 无（**硬缺口**；`09-strong-quote-bot` 只覆盖引用回复） |
| 5 | 命中「兴趣话题 / 性格话题」 | **话题滚动**（与场景 2 共用收敛点） | 话题指纹 vs 兴趣池的粗匹配（可选，用于省 LLM 调用） | 兴趣池条目 + 该话题当前是否已有 bot 发言 | 最高（「怎么什么都插一嘴」） | 无（**硬缺口**；当前 Gate 的 `criteria` 是单一常量，无兴趣池概念） |

**关键读数**：五个场景里有两个是**事件驱动**（1、4），两个是**话题滚动驱动**
（2、5），一个是**定时器驱动**（3）。这就是「不是并列五分支」的第一层证据：
它们连**判定的时机**都不一样。把这五者摊平成一个 `switch`，等于承认
「每条消息都要把五种情形都想一遍」——那是成本和噪声的双重灾难。

### 1.1 场景之间的重叠与「取第一个」的真实含义

业务方声明场景互斥。工程上要补一句：**互斥是策略，不是事实**——
同一条消息天然可能同时命中多条（例：「@bot 这个图能画吗」同时命中 1 和 4；
「谁有 xx 的资料」沉默 10 分钟后命中 3，同时因为 xx 在兴趣池里也命中 5）。
所以「取第一个」的真实含义是：

> 在一次仲裁里，多个场景同时成立时，**排序最小者获胜**；
> 其余场景的原因不丢失，作为 `alsoMatched` 进 trace（用于事后调序）。

这条规则必须在**唯一一处**实现（仲裁层），不能散落在各个预筛规则里：
只要有一处规则「先拦了再说」，顺序就再也不是全局一致的了。

### 1.2 一个必须修掉的既有弱点：场景 3 的「已应答」判定

现有 `10-strong-open-question` 的答案窗口重查逻辑是**纯本地启发式**：
「窗口内有其他发送者发言」就认为问题已被应答。这在真实群里几乎必然误判
（有人插一句「哈哈哈哈」也算应答），于是两条路都错：要么问题被错误作废
（该介入而不介入），要么启发式放宽后变成抢答。

本方案的做法是**把这个判定交回仲裁层**：90 秒窗口到期只意味着「问题进入
待确认」，台账把它标成 `open` 并连同**窗口内的全部后续发言**一起进转录，
由 LLM 回答「这个问题是否已经被回答了」。理由：

- 这不需要**额外**的 LLM 调用——仲裁本来就要跑，只是多问一句；
- 它把「是不是被回答了」从关键词启发式升级为语义判定，而这正是 LLM 的强项；
- 判定结果落回台账（`answered` / 仍 `open` → 进 T2 探针），会计账可审计。

代价是台账状态依赖 LLM 输出，因此**解析失败一律保持 `open` 而不置 `answered`**
（fail-open：宁可多探一次，也不要把真问题丢掉）。

## 2. 三个平面的架构

```
┌── 平面 A：触发（deterministic，本地，零 LLM 成本）───────────────────────┐
│  A1 消息事件      : 每条 observed 消息 → 本地预筛（05/06/07/04）+ 场景预筛  │
│                     · scene-4 别名命中      → 立即评估                    │
│                     · scene-1 窗口内 + 话题连续 → 立即评估                 │
│  A2 问题台账      : 问句挂起 T1(90s) → 无人应答 → 立即评估                 │
│                     仍无人应答 → 二次探针 T2(10min) → 再次评估（最多一次）   │
│  A3 话题滚动       : 每 N 条(默认 20) 或 M 分钟(默认 5min) 无仲裁则收敛一次  │
│                     → 场景 2 / 5 的评估机会                               │
│  A4 相位/冷却     : FOCUS/FADING/COLD 决定 A3 的采样率与是否需要先答后插    │
└──────────────────────────────┬──────────────────────────────────────────┘
                               ▼
┌── 平面 B：仲裁（单次 LLM 调用，语义，唯一语义判定点）─────────────────────┐
│  scene-arbitrate：输入 = 有序场景清单(criteria) + 转录 + 话题摘要             │
│                        + 问题台账 + bot 状态块 + 能力清单                    │
│  输出 = { scenario, decision, confidence, reason, evidence?, directive? }    │
│    · scenario ∈ {SCENE-1..5}，多命中取 order 最小者                          │
│    · decision ∈ speak | wait | silent                                      │
│    · wait 语义 = 「现在不该说，但 T 秒后值得再看」（复用现有 defer 通道）        │
│    · 解析失败 / 超时 / 未知 scenario → silent（fail-closed，沿用现有纪律）      │
└──────────────────────────────┬──────────────────────────────────────────┘
                               ▼
┌── 平面 C：硬约束（deterministic，否决式，对 5 个场景一律生效）─────────────┐
│  30 硬限流 → 31 焦点预算/每话题一次 → 33 夜间静默 → 32 准入 try              │
│  任一否决 = 放弃（不排队）；场景优先级不改变本条链的任何一层的判定            │
│  通过 → 合成介入 turn（携带 directive）→ TurnRunner → Responder              │
└──────────────────────────────────────────────────────────────────────────┘
```

三平面划分的三个好处，正好对应现有实现的三处接缝：

| 平面 | 现有接缝 | 本方案的动作 |
|---|---|---|
| A 触发 | `intake` 链 + `RuleVerdict.defer` + watcher 的定时器 | 新增场景预筛规则与「话题滚动」调度器；**不改**链式短路契约 |
| B 仲裁 | `evaluate` 链的 `20-semantic-gate` | 输出契约加字段；判定标准从常量 `criteria` 变为**有序场景清单** |
| C 硬约束 | `speak` 链（30/31/32/33） | 仅新增「每话题一次」台账判据；其余不改 |

**为什么仲裁必须是一次调用而不是五次**：五次调用不仅成本 ×5，而且会引入
**跨调用的顺序不可复现**（并发完成顺序决定谁先返回）。一次调用里由
**prompt 内的固定顺序**决定胜负，是唯一能在「同时命中」时保证确定性、
且能被离线回放复现的做法。这也顺带解决了成本问题。

## 3. 数据模型：场景之外真正要新建的三样东西

前两节的架构可以直接长在现有代码上；真正的工作量在状态层。

### 3.0 先说一个反直觉的取舍：**不做「每场景独立状态」**

审计确认了一件关键事实：现有 `ConversationWatchState` 的每一项状态
（`spokeAt` 限流窗口、`lastEvaluateAt` 冷却、`phase` 相位、`focusSpokeCount`、
`pendingMerge`、`unevaluatedCount`）**全部挂在会话键上**，没有任何话题或场景维度。
于是最自然的下一步就是把状态也按场景切开——**本方案明确反对**，理由三条：

1. **状态维度一多，否决链的口径就散了**。防刷屏要回答的是「这个群里 bot
   最近说了多少话」，这是**跨场景**的问题；分场景记账后，每个场景都在自己的
   额度内合规，合起来仍然刷屏（经典的额度漏洞）。
2. **场景不是稳定的实体**。同一条消息可能命中 2 个场景，按场景记账会把
   一次发言重复计入两处；而「取第一个」又要求只有一个赢家，账目与事实对不上。
3. **维护成本不对称**。加一个场景要同时改状态机、迁移表、预算表、统计表——
   这正是 P0 方案 §5.1 三条纪律想避免的「规则埋在实现里」。

**结论：状态只按「会话 / 话题 / 问题 / 花费窗口」四个维度记账，永不按场景记账。**
场景只出现在两个地方：**仲裁的输入与输出**（谁赢、为什么），与
**trace / 指标**（哪个场景命中多、被否决多）。「每场景独立限流」这类需求，
正确的表达是「每话题上某类介入至多 N 次」——用话题与相位表达，不用场景表达。

这条取舍同时决定了实现顺序：**先有话题与问题台账（S2/S3），场景标签才有意义**
（S1 只固定接缝，不指望 5 个场景立刻都有独立判据）。

### 3.1 `Topic`（话题）—— 场景 2、5 的地基

```ts
interface Topic {
  id: string;              // 话题指纹（见下）
  convKey: string;         // onebot:g<群号>
  startedAt: number; lastAt: number;
  participants: Map<string, number>;  // 发言人 → 末次发言时间
  messageIds: string[];    // 归入本话题的消息 id（有界，用于渲染）
  botSpoke: boolean; botSpokeAt?: number; botSpeaks: number;  // 介入记账
  lastArbitratedAt?: number;   // 上次走过仲裁的时间（话题滚动的节流依据）
}
```

- **话题边界怎么划**（工程上的取舍，不要过度设计）：本地做**连续性聚类**——
  新消息与「当前活跃话题」算一个廉价相似度（关键词/实体交集 + 时间间隔
  < 90s + 有无 @/引用锚点），不相似则开新话题，旧话题进 `COLD`。
  这里**不上 LLM**（每条消息一次 embedding 或一次分类都是不可接受的成本）；
  话题的语义收敛交给 3.3 的滚动摘要（每 N 条一次）。
- **为什么必须有话题维度**：现有实现的限流与相位都是**会话级**
  （10 分钟 ≤3 次这类口径，见 P0 方案 §9.3）。会话级口径无法回答
  「这个话题我已经插过一次嘴了吗」——而这恰恰是场景 2、5 最需要的判据。

### 3.2 `QuestionLedger`（未答问题台账）—— 场景 3 的地基

```ts
interface PendingQuestion {
  id: string;
  topicId: string; asker: string;
  text: string; askedAt: number;
  probes: number;              // 0 → 首次探针 → 1 → 二次探针（上限）
  state: 'open' | 'answered' | 'expired' | 'silenced';
}
```

- **谁把问题写进台账**：`10-strong-open-question`（现有的问句预筛）——
  它已经在做 `defer(90s)`，把它从「延迟重入」改造成「**登记 + 排探针**」
  即可，改动面很小。
- **谁把问题关掉**：三种关闭路径，优先级从高到低——
  1. 同一话题内有他人的实质回复 → `answered`（**用仲裁时的 LLM 判定来关**，
     不额外加一次分类调用：转录里带上「台账中仍挂起的问题」，让 LLM 顺便
     回答「这些问题是否已被回答」）；
  2. 二次探针到期仍无人应答 → 再次评估，仍然 `silent` / 被硬约束否决 → `expired`；
  3. 提问人在窗口内自己补充或撤回 → `answered`。
- **为什么不能只靠定时器**：90 秒探针对「群里没人」有效，对「大家在打字」
  会误伤。二次探针（10 分钟）+ 转录里显式标注挂起时长，让 LLM 拿到
  「已经没人理它 10 分钟了」这一事实，比在代码里堆阈值可靠得多。
- **台账必须进仲裁 prompt**：`【挂起问题】09:12 张三：谁能跑一下这个爬虫？（至今 11 分钟无人应答）`。
  这既让场景 3 可判，也让场景 3 与场景 2 的边界变得清晰
  （前者是「具体问题没人接」，后者是「话题在持续但没人问 bot」）。

### 3.3 `TopicSummary`（滚动话题摘要）—— 场景 2、5 的成本解法

- **做法**：每个话题每 N 条消息（默认 30）或 M 分钟（默认 5）触发一次
  「摘要 + 关键词 + 未答问题候选」的小模型调用，结果写回 `Topic`。
  仲裁时给 LLM 的是**摘要 + 最近 10 条原文**，而不是 30 条原文。
- **为什么值得多花这次调用**：它把场景 2/5 的**输入长度从 O(消息数) 压成 O(1)**，
  否则长话题的转录会线性膨胀到 token 上限，仲裁质量反而下降。
- **注意**：摘要调用与仲裁调用都是 LLM，必须共用一个全局并发闸
  （现有 `gate.maxConcurrent` 默认 2 的先例），否则长群里会出现
  「摘要风暴」把 API 配额吃光。

### 3.4 `InterestProfile`（兴趣 / 性格话题池）—— 场景 5 的地基

- **形态**：一份**人可读、可审计**的清单文件（建议
  `persona/interests.md`，与 persona 同源），条目形如：

  ```yaml
  - id: plotting
    topic: 数据可视化 / 画图 / 图表
    why: 我有 matplotlib 与文件出站能力，能直接给图
    say: 只在话题停在「没有结论」或「没人动手」时补一句能立刻用的结果
    budget: 每话题最多 1 次
  ```

- **谁维护**：**不做运行时自我修改**（与 P0 方案 §1 非目标一致）。
  建议闭环：每天一次离线任务，从当日旁听转录里提出候选兴趣条目
  （「这个话题群友聊了 6 次、每次 bot 都有信息增量」），**产出 diff 交人审**，
  再随镜像发布。这既拿到「LLM 设定兴趣话题」的效果，又不给 prompt 注入面
  开后门。
- **判定时怎么用**：整份兴趣池进仲裁 criteria 的 `SCENE-5` 段
  （条目数建议 ≤15，超了先按命中次数排序截断——prompt 预算也是预算）。

### 3.5 能力清单（场景 2 的第二个判据）

业务场景 2 里「有自己可以提供的能力（如绘图等）」需要在 prompt 里可判。
**建议不做成代码级能力注册表**（一张会腐烂的表），而是在场景 2 的
criteria 里枚举**能力域**（查资料 / 跑代码与脚本 / 数据与图表 / 文件生成与转换 /
多步任务），由 persona 保证与实际工具一致。若某天需要更硬的判据，
再升级成「能力域 → 工具名」的结构化表（留作开放问题，见 §14）。

### 3.6 一个必须补的输入缺口：**bot 自己的上一句不在转录里**

审计发现的第一个、也是最致命的输入缺口，直接决定场景 1 能不能做：

> 旁听缓冲只收**非 @ 消息**（`transcript.ts` 渲染时还会把已走 @ 路径的条目
> 用 `addressed` 标记滤掉）。bot 被 @ 后的回复是走 @ 路径发出的，**因此不进
> 缓冲**——也就是说，仲裁看到的转录里**没有 bot 刚说过的那句话**。

而场景 1 的判据恰恰是「与 bot 上一条发言同一话题的追问」「bot 是否已经回答过」。
现状下 LLM 只能靠 `<bot状态>` 里的「距上次发言 X 秒 / 近 10 分钟介入次数」
这类**计数器**去猜 bot 说过什么——这不可能判对。

**修法（属于 S1 的范围，不额外花 LLM 调用）**：

1. `transcript.ts` 增加 `renderBotReplies(state, limit)`，把**本群 bot 最近的 1–2 条
   已发送回复**（从 `botMsgIds` 对应的账本 / Responder 投递记录取，带时间戳）
   渲染成单独一块 `<bot最近发言>`，与转录、`<bot状态>` 并列进仲裁输入；
2. 转录里的 bot 历史发言要**显式标注发言人**（现状是普通 `[名字] 文本` 一行，
   模型分不清哪句是自己说的）——保守做法是加标记（如 `[我(bot)]`）而不是
   从转录里剔除，因为「我上次说了什么」正是判断信息增量的关键；
3. 若某条 bot 回复已被平台以 observed 形式回推（自回显），去重口径要与
   `botMsgIds` 对齐，避免同一句话出现两次。

这条缺口也解释了为什么「续聊」在实测中容易显得笨：判定方其实是在**不知道自己
刚才说了什么**的情况下决定要不要接话。

## 4. 场景注册表与仲裁契约

### 4.1 目录形态：场景与规则同构

沿用「规则 = 文件夹（REQUIREMENT.md + rule.ts + rule.test.ts）」的既有纪律，
场景也做成文件夹——因为它同样满足「需求即真相源」：

```
src/intervention/scenes/
  SCENES.md              # 场景清单与顺序的自然语言描述（与 registry 一致性由测试校验）
  scene-1-continuation/  # REQUIREMENT.md（含 criteria 段）+ scene.ts
  scene-2-ongoing-discussion/
  scene-3-unanswered-question/
  scene-4-bot-reference/
  scene-5-interest-topics/
  registry.ts            # 按 order 装配，唯一 import 各场景的地方
```

`scene.ts` 只提供两样东西：**预筛谓词**（本地、纯函数）与
**criteria 片段**（自然语言，进 prompt）。判定与发言决策都在仲裁层，
场景文件里不出现阈值硬编码之外的逻辑。

### 4.2 契约（接缝代码见 `src/intervention/scenes.ts`，本分支仅作草案）

```ts
export type SceneId = 'scene-1' | 'scene-2' | 'scene-3' | 'scene-4' | 'scene-5';

export interface SceneDefinition {
  id: SceneId;
  order: number;             // 越小越优先；「取第一个」= order 最小
  name: string;              // 短名，进日志与 /listen scenes
  enabled: boolean;
  triggers: SceneTrigger[];  // 'message' | 'question-probe' | 'topic-roll' | 'speak-followup'
  criteria: string;          // 进 LLM prompt 的自然语言段（来自 REQUIREMENT.md）
  precheck?(ctx: ScenePrecheckContext): SceneHit | undefined;  // 本地预筛，纯函数
}

export interface SceneVerdict {
  scenario: SceneId;
  decision: 'speak' | 'wait' | 'silent';
  confidence: number;        // 0..1，进 trace 与预算（低置信不让过）
  reason: string;
  alsoMatched?: SceneId[];   // 同时命中的其他场景（调序依据）
  evidence?: string;         // 场景 2/3：被纠错的原文或那个没人答的问题
  directive?: string;        // 交给介入 turn 的「该说什么」的要点
}
```

三个设计要点：

1. **`precheck` 是纯函数且可返回 undefined**——它只做「这个场景有没有
   可能成立」的廉价判断（别名命中、窗口内、台账非空）。它**不否决**其他场景，
   只决定「本次仲裁要不要把这个场景写进清单」。
2. **`triggers` 把「时机」编码进了场景定义**——场景 2/5 永远不在
   `message` 触发下出现，从根上避免「每条消息都判一次兴趣话题」。
3. **`order` 是全局唯一的顺序来源**，registry 按它装配，prompt 按它渲染，
   trace 按它记账。测试只需断言 registry 有序且与 SCENES.md 一致
   （与现有 `index.ts` ↔ `CHAIN.md` 的一致性测试同构）。
4. **全局保险不进场景判据**：接缝里提供一个统一入口 `collectSceneHits()`，
   它做两件全球一致的事——只跑该触发面下的场景，以及**「没人理我就停」**
   （`unansweredStreak ≥ 2` 时全体沉默，任何用户发言归零）。
   这类「会话级事实」绝不能写进某个场景的 `precheck`，否则场景之间会互相
   绕过（§3.0 同一条纪律的延伸）。

### 4.3 场景各自的判定权威（不同场景，不同门槛）

「取第一个」只解决冲突，不解决「凭什么是它」。每个场景的 speak 门槛应当
**显式写在自己的 criteria 里**，且**风险越高门槛越高**：

| 场景 | speak 门槛（写进 criteria 的要点） |
|---|---|
| 4 指代 | 明确指出是「在对 bot 说」而非「在议论 bot」；若只是提及 bot 的名字但话题不需要 bot → silent |
| 1 续聊 | 与 bot 上一条发言同一话题，且**尚无人（含提问者自己）解决**；只是继续闲聊 → silent |
| 3 无人应答 | 问题仍未被回答 + 问题在能力域内 + 已静默足够久；**若群里有人正在回应 → wait** |
| 2 持续讨论 | 三个判据至少一个成立（可提供能力 / 有可答问题 / 有事实性错误）**且** bot 的话有信息增量；纯观点碰撞、情绪话题 → silent |
| 5 兴趣 / 性格 | 话题停在**没有结论或没人动手**处，且 bot 能补一句可立即使用的结果；每话题至多 1 次 → 超过即 silent |

### 4.4 事实性错误要区分「可确证」与「观点分歧」

场景 1、2 都含「用户的发言存在事实性错误」这一判据，这是**最容易翻车**的
一条（数字、单位、代码报错、常识——纠对了加分，把观点当错误纠正会招骂）。
建议在 criteria 里写死三层纪律：

- **只纠可确证的事实**（可枚举、可计算、可查证），且必须给出 `evidence`
  （被纠错的原文片段）；
- **观点、偏好、预测、价值判断 → silent**（明确列举）；
- **不确定 → silent**，不要「温和地补充一点」（那正是「好为人师」的味道）。

## 6. 成本模型（为什么这样切才对）

设：群消息速率 `r` 条/分钟，其中命中场景 4/1 的比例 `p_evt`，
话题滚动周期 `N` 条。

| 方案 | LLM 调用次数 | 现实后果 |
|---|---|---|
| 每条消息判 5 个场景 | `5r` | 不可接受（一个 60 人群的活跃时段 ≈ 每分钟几十次） |
| 每条消息判一次（含 5 场景合并） | `r` | 仍然偏高：绝大多数消息毫无价值（06 无文本 / 05 @ 别人早已拦掉） |
| **本方案：事件触发 + 话题滚动 + 问题探针** | `≈ p_evt·r + r/N + 探针次数` | 活跃群里默认 N=30 时约为 `r/30` 量级；再加既有去抖（13）与冷却（12）二次削峰 |

再叠加已有的三道成本阀：`12-eval-cooldown`（冷却期内连预筛都不做）、
`13-sampling-debounce`（当前默认 `evaluateEvery=6`、`silenceDebounceMs=20s`，
已经是「采样 + 静默去抖」两道）、`gate.maxConcurrent`（全局并发）
以及谷时段直接不评估（规则 03）。**结论：场景化不应该增加调用次数，
只应改变每次调用的内容**——这是判定「架构是否切对」的硬标准。

`N`（话题滚动周期）的建议起点是**比现有 `evaluateEvery=6` 更保守的 30 条**：
现有的采样是「会话级、每 6 条给一次机会」，本方案要加的是「话题级、每 30 条
收敛一次摘要与仲裁」。两者不冲突——前者的机会大多数会被 12/13 与硬约束消化，
后者才是场景 2/5 的真实入口。上线时先按 N=30 起，看回放数据再收紧。

## 7. 可观测性与调参闭环（不做这一步，阈值只能靠猜）

1. **仲裁记录（JSONL）**：每次仲裁落一条
   `{ts, convKey, trigger, transcriptHash, sceneOrder[], verdict{scenario,decision,confidence,reason,alsoMatched}, speakChain[], outcome}`；
   转录与状态块**同时快照**（有界、可关闭）。
2. **离线回放**：拿历史快照重跑 gate（真实 LLM，但零发言、零打扰），
   用于比较「改顺序 / 改 criteria / 改阈值」的差异。这是唯一能回答
   「换个顺序会怎样」的方法，也让 §11 的调序决策有数据支撑。
3. **指标**（建议直接进 `PipelineStats`）：
   - 分母：各场景 `precheck` 命中数、进入仲裁数；
   - 分子：各场景 `speak` 数、被各硬约束否决数（分原因）；
   - **质量代理**：介入后 120s 内是否有他人接话（正）、
     是否被要求「别插嘴」/被管理员静默（负）、
     场景 3 的问题是否在介入后被他人回答（说明本来就有人会答）。
4. **成功判据**：不要用「介入次数」当 KPI，用「介入后话题被推进的比例」
   与「被厌恶的比例」。前者靠回放统计，后者靠 `/listen why` 的人工反馈入口。

**一个必须先补的基础设施**：审计确认**控制面完全没做**——
`watcher.setRuntimeEnabled()` 至今**没有任何调用点**，`/listen` 命令
（含 §5 表里那两条）在 `src/` 里不存在，P0 方案 §10 提到的
`stateDir/listen-override.json` 也没有实现。因此本方案涉及的命令面
（`/listen scenes`、`/listen why`、按群开关某场景）不是「改一下」，而是
**从零建**，并且要连带决定「运行期开关要不要持久化、存在哪里」。

另一个口径细节：现有 `halts` 是按**规则名**计数的（`InterventionSnapshot`），
而各规则 `REQUIREMENT.md` 里声明的 `stats:` 字段（例如
`halt_night_silence`）**代码并没有消费**。本方案要做到「按场景看否决分布」，
就必须把场景标签一路带进 chain trace 与统计——这是 §12 审计清单里的
第 6 处改动（`chain.ts` 的 `ChainTraceStep` / `formatTrace`），别漏掉。

| 期 | 内容 | 可独立上线 | 验收 |
|---|---|---|---|
| S1 | 场景契约 + registry + 本地预筛（4、1）+ 仲裁输出契约扩展（单场景化，criteria 单常量 → 有序 5 段） | ✅（行为等价于现状，仅输出更丰富） | 契约测试 + 回放对比：S1 前后 speak 决策一致率 ≥95%（否则说明 prompt 改动有副作用） |
| S2 | 话题聚簇 + 滚动摘要 + 每话题预算（场景 2、5 可用；`31-focus-budget` 加话题否决） | ✅ | 合成转录用例：同一话题二次介入被否决；长话题 token 不随消息数线性增长 |

| S4 | 仲裁记录 + 离线回放 + 指标（含控制面最小集：`/listen scenes` / `/listen why`，**当前不存在**）；有数据后引入**按场景置信度加权的分位数预算**（§13.2），取代「优先级开天窗」 | ✅ | 回放同一份快照两次，verdict 一致（确定性）；场景维度指标可在控制面读出；分位数预算下仍**不得超过**硬限流上限 |
| S5 | 兴趣池文件 + 每日候选生成（产出 diff 交人审） | ✅ | 生成器只产出候选文件，**没有任何自动写入生效路径** |

顺序理由：S1 先固定接缝（否则后面每个场景都要改一次契约）；S2/S3 是纯状态层，
可以并行；S4 必须在调参之前（否则 S5 的兴趣池没有数据支撑）；S5 最后做，
因为它是唯一带「LLM 改自己的判据」味道的部分，风险最高、收益最依赖前四期。

## 9. 风险清单与硬约束

| 风险 | 表现 | 硬约束 |
|---|---|---|
| 刷屏 | 场景 1/4 因为「被点到名」反复发言 | 场景优先级不豁免 speak 链；每话题 ≤1 次；10 分钟 ≤3 次全局 |
| 抢答人类 | 场景 3 在别人正在打字时插话 | 双探针（90s → 10min）；criteria 明确「有人正在回应 → wait」 |
| 把观点当错误纠正 | 场景 1/2 的事实性纠错误报 | 只纠可确证事实 + 必须给 `evidence` + 观点/预测/价值判断列举为 silent |
| 蹭话题 | 场景 5 无差别接话 | 兴趣条目 ≤15 且每条带 `say` 约束；每话题 ≤1 次；命中率进指标，低于阈值即下线该条目 |
| **替他人发言** | 被追问时替群友「代言」、替人下结论 | **硬约束：任何场景都不得替他人发言**（openclaw 封禁案例的直接根因，§13.4）；写进 criteria，并进 S1 验收用例 |
| 没人理还继续说 | 连续介入而群里无人回应 | 未回应计数：任何用户发言立即归零，累计 2 次即暂停主动发言（§13.3） |
| 纯沉默触发 | 只因「很久没人说话」就发言 | 禁止：无新消息不允许触发探针（MaiBot 的两道保险，§13.3） |
| 反复撞同一堵墙 | 同一问题被仲裁否决后无限重探 | 台账新增 `silenced` 状态：拒绝也落标记（§13.3） |
| 提示注入 | 转录里含「忽略以上指令」类内容 | 沿用现有不可信输入边界声明（`<群聊转录 说明=…>`）；兴趣池只从**人审过**的文件来；边界要**逐条注入**（紧邻决策点），不能只靠会话开头的 system prompt（§13.4） |
| 成本失控 | 摘要 + 仲裁双调用叠加 | 单次评估 ≤1 次 LLM 调用；全局并发闸；N/M 可调且默认保守 |
| 隐私 | 旁听内容长期留存 | 沿用 P0 现状（内存 ring buffer，不落盘）；仲裁快照**有界 + 可关闭**，默认只在开启回放时落盘 |

## 10. 与「不做什么」的边界

- **不做**：陪聊拟人化（好感度、表情包、定时破冰）、单聊介入、运行时自我修改
  兴趣池、打断在途 turn、多轮自主追问（介入后继续自己接自己的话）——
  与 P0 方案 §1 非目标一致，本方案不放开任何一条。
- **不做两段式场景识别 + 决策**（成本 ×2、顺序不可复现）。
- **不做 5 条独立 LLM 判定链**（同上）。
- **不把场景分类结果当发言许可**（分类只决定「以什么姿态说」，许可权在平面 C）。

## 11. 需要维护者拍板的决策点

1. **场景顺序**：建议 `4 → 1 → 3 → 2 → 5`（被点到名 → 刚聊过的延续 → 时效最紧 →
   最需克制 → 最易饿死）。业务方给出的编号（1–5）直接当顺序会使「指代」场景
   永远排在「续聊」之后，在「@bot 之后别人提到 bot」的情形下产生反直觉结果。
2. **单次调用 vs 多次调用**：本方案主张单次（§0.5 / §2）。若坚持每场景独立
   criteria，需要接受成本 ×N 与顺序不可复现，或改为串行（延迟 ×N）。
3. **场景优先级能否突破限流**：本方案 S1–S3 主张**不能**（§0.3）；审计已确认
   「介入 ≠ 被 @」在记账层面本来就成立（`spokeAt` 只记主动介入，@ 回复
   既不进该窗口也不计介入类统计，见 P0 方案 §9.3 的 force 路径），
   因此不能拿「@ 路径不受限」当类比要求介入也放宽。
   但调研提供了一个更好的第三条路（§13.2）：**用按场景置信度加权的分位数预算
   取代「开天窗」**——高优先场景自然突破，且不产生绕过记账的后门。
   建议 S4（有回放数据后）再引入，S1–S3 先用简单可解释的硬限流。
4. **兴趣池的维护形态**：静态人审文件（本方案建议）还是每日生成的候选 + 自动生效？
   调研补充：业界最省事的形态是**静态关键词表 + hint 注入**（不直接放行，§13.1-3），
   建议 S5 先做这个，再考虑生成候选。
5. **话题聚簇是否可接受启发式**：本方案用「关键词交集 + 时间窗 + 锚点」的
   廉价聚类，允许话题切分错误（错误代价只是「多开一个话题」而不是「误发言」）。
   若要求话题切分准确，则需 embedding，成本模型要重算。调研的对照：np 用
   `mention + embedding cosine + keyword + speaker_continuity + proximity` 五项加权、
   阈值 0.45，**五项全满也只有 0.65**，说明其阈值偏松、在高噪声群里会过度合并——
   照抄权重不可取。
6. **台账探针的次数与间隔**：建议 T1=90s（复用现有答案窗口）、T2=10min、
   上限 2 次。这直接决定场景 3 的敏感度。
7. **谁有权调阈值（调研新增的第 6 个设计轴）**：Koala II 的修复手段是把固定阈值
   改成**用户可随时调整的三档**（high=90 / medium=75 / low=50），并暴露
   「在频道还是在线程里发言」。落到本项目 = 群管理员能否用
   `/listen` 调某场景的敏感度、以及这个调整要不要持久化（§7 的控制面）。
8. **通道确认（最高优先，可能推翻预算设计）**：官方 Bot API 的主动消息是
   **每群每月 4 条**（2025-04-21 起主动推送能力已下线，§13.6）。本方案的预算
   口径只在 OneBot 通道成立——**请确认「本期是否只做 OneBot」**，
   否则场景 3/5 的实现形态要整体重写。

## 12. 独立审计：现状能与不能（带行号证据）

本节是对 `feat/topic-intervention-p0` 的一次只读审计结论（行号口径为该分支的
文件行号，下文路径不加分支前缀）。它支撑了前文的所有判断，也暴露了
**P0 方案文档自身已经漂移**——实施时必须以代码为准。

### 12.1 可以直接躺在上面做场景化的既有资产

1. **「按顺序取第一个命中」不需要新机制**：`chain.ts` 的 `runChain`
   本来就是顺序遍历 + `halt` 短路 + `marks` 累积；谁先 `mark`、谁被后面的
   规则看到，都是现成语义。场景化要新的是**判定内容的组织**，不是控制流。
2. **规则文件夹 + 生成口是低边际成本的落地通道**：新增一条规则 ≈
   一句自然语言需求 + 一次草稿确认 + 一次 git review，校验管道
   （静态纪律 → `tsc` → `vitest` → 链冒烟，失败最多 3 轮自我修复）
   自动把关。生成口已有实产（`33-night-silence-veto` 就是生成出来的）。
   代价：生成器会**直接写进 `src/`**，校验失败还会把规则夹 `rename` 到
   `_rejected/`——操作时要有 git 兜底。
3. **共用前置层齐全**：去重（`04`）、两档冷却（`12`：60s / 强信号 15s）、
   两档硬限流（`07` + `30`：10 分钟 3 次、1 小时 8 次）、相位与焦点预算（`31`）、
   夜间静默（`33`）、准入 try（`32`）、开关 / 白名单 / 谷时段（`01`/`02`/`03`）
   全部与场景无关，可原样作为「所有场景共用前置层」。
4. **投递链路可承载场景化载荷**：`synthesizeIntervention` 的 prompt 文本是
   可替换的，`NormalizedMessage.origin` 已经在 `core/connector.ts` 里定义了
   `'user' | 'continuation' | 'intervention'`，`turn-runner` 已经按
   `origin === 'intervention'` 三分支（跳过冷启动回放 / 跳过媒体块 / 跳过进度回执）。
5. **准入的「绝不排队」语义**已经实现：`AdmissionGate.tryRunExclusive` +
   非阻塞的 `Semaphore.tryAcquire` / `KeyedMutex.tryRun`，被拒即放弃并计
   `interventionsDroppedBusy`。

### 12.2 硬缺口（不是「再加一条规则」能解决的）

| # | 缺口 | 证据 | 本方案在哪解决 |
|---|---|---|---|
| 1 | **状态只有会话维度**，没有话题 / 问题维度 | `state.ts` 的字段全部挂在会话键上（缓冲、`spokeAt`、`lastEvaluateAt`、`phase`、`focusSpokeCount`） | §3.1–3.3 新增话题与台账；§3.0 明确**不**做每场景状态 |
| 2 | **场景标签通道不存在** | `GateVerdict` 只有 `{decision, reason}`；`parseGateVerdict` 只认三元 decision；`RuleMarks` 无场景位；trace 无场景位 | §4.2 契约 + §5 的 8 处改动（含 `chain.ts`，最易漏） |
| 3 | **没有「多候选取第一个」的仲裁表达** | `RuleVerdict` 只有 `pass/mark/defer/halt`，链只有层内短路 | §4.2 `selectScene`（唯一实现）+ 契约测试 |
| 4 | **没有每话题预算** | 只有全局焦点预算与会话限流；`spokeAt` 只记介入次数，无话题归属 | §3.1 的 `Topic.botSpeaks` + §5 的 `31-focus-budget` 改动 |

| 6 | **限流与统计不分来源、不分场景** | `origin` 止步于 `turn-runner`（不传 Responder）；`spokeAt` 与 @ 路径各记一套、互不相干；`halts` 按规则名而非场景；`REQUIREMENT.md` 里的 `stats:` 字段**代码未消费** | §7 指标 + §5 的 `chain.ts` 改动 |

### 12.3 实施前必须先认下的既有行为（容易踩的坑）

1. **相位迁移发生在「投递成功之后」**，不是「speak 链全过」
   （`watcher.ts:598-606`）：准入被拒时 `spokeAt` 与相位都不动。
   新增的每话题记账必须挂在**同一个成功点**上，否则账目会与事实不符。
2. **晋升会重置续聊窗口**（`watcher.ts:349-353`）——「其他人的追问走晋升路径」
   不是一个中性选择，它会让提问者的窗口被续命。场景 1 的其他人追问因此
   走**介入路径**（§5 已按此写）。
3. **「介入 ≠ 被 @」在记账层面已经成立**：`spokeAt` 只记主动介入，
   @ 回复既不进 `spokeAt` 也不计介入类统计——场景优先级不能拿
   「@ 路径不受限」当突破限流的类比理由。
4. **`defer` 的代价不只在等待**：`10-strong-open-question` 重入时的
   「是否已被应答」判定是纯本地启发式（窗口内有他人发言即算应答），
   这是 §1.2 要修的目标；同时注意**消息在 `defer` 时就已经进缓冲**
   （`watcher.ts:451`），台账改造不要重复入缓冲（`pushEntry` 有幂等保护，但别依赖它兜错）。
5. **转录有三条硬约束**：`addressed` 条目被滤除、`slice(-limit)` 取最近
   （默认 30 条）、正文超 `maxChars=4000` 从**头部**截断。话题摘要若不控制
   长度，会把更早的原文挤掉。
6. **FADING 相位的真实语义**是「采样阈值减半」（`13` 号规则），
   不是「停止评估」；`07` 号规则拦的是**限流窗口**，与相位无关。

### 13.1 三个直接验证本方案的发现

1. **没有任何项目做「场景标签 + 按优先级取第一个」的 taxonomy。**
   最接近的是 np 的 `TurnSemanticFrame`：**一次调用同时**输出
   `recommend_silence`（布尔门）+ 7 类 `conversation_scenario` + 6 类意图 +
   语气字段——即「门与场景标签可以一次出」已有生产级先例，但它的场景枚举
   **只影响回复风格，不参与放行裁决**。另一侧，DiscussLLM 标了 5 类干预类型
   （含 Factual Correction），却**只用于合成数据**，真正训练的分类器是
   纯二分类 SILENT/SPEAK。
   → 对本方案的含义：**单次调用出「场景标签 + 是否发言」是对的**（§4.2 已按此设计），
   但**场景标签不要用来放行**——它的价值在于（a）驱动说法/形态，
   （b）进 trace 与指标支撑调序。这与 §0.3「优先级不决定能不能说」一致。
2. **「按话题记账」在开源实现里查不到严格先例。** np 的配额键是
   `(日期, 用户, 场景)`；`pending_topics` 只有单条状态位。本方案 §3.1 的
   `Topic + 每话题 ≤1 次` 属于自研部分，没有现成实现可抄，**实施时要多花测试成本**。
3. **兴趣池的正确形态是「hint 注入」而不是「命中即放行」。** 唯一完整实现的
   JEV 用纯字符串 `contains` 本地匹配兴趣关键词（零成本），命中后**只在判定
   prompt 里注入一句「这符合你的人格兴趣，可以更积极」**，并且未命中时也显式
   留后门（「若与你人格相关仍可参与」）。
   → 本方案 §3.4 的 `matchedInterestIds` 因此**只作为预筛与提示**，
   最终仍由仲裁决定（`SCENE-5` 的门槛是五者最高的）。

### 13.2 一处需要修正的设计：优先级与限流可以不再对立

我在 §0.3 / §11.3 主张「场景优先级绝不突破限流」。调研找到了一个更好的答案
（**MaiBot `DynamicReplyGate`**），它把这对矛盾**消解**掉而不是选边：

> 不设固定上限，而是让实际发言数逼近 `频率 × 预计发言次数`：
> `目标 = frequency × (Σ 各场景发言概率)`；
> **阈值 = 窗口内候选概率降序累加到「保留额度」那一档的概率值**——
> 即阈值是**分位数而不是常数**。高优先级场景的 `reply_likelihood` 天然更高，
> 在分位数阈值下**自动突破**，不需要开后门，也就不会出现
> 「后门绕过记账导致刷屏」。源码注释里还写明「**只收紧不放宽**」：
> 一波消息刚到时预计数先涨、实际回复还没跟上，若据此放宽，
> 等这波过去就再也收不回来，回复会系统性偏多。

**对本方案的落地建议（放进 S4，不放进 S1/S2）**：

- S1–S3 仍然用确定性的硬限流（`30`/`31`）——它简单、可解释、fail-closed；
- S4 有了仲裁记录与回放数据**之后**，再引入「按场景置信度加权的分位数预算」，
  取代「场景优先级开天窗」这种表达；
- 概率估计必须来自**本项目的回放统计**（各场景命中率 × speak 率），
  MaiBot 的权重与它的 Planner 日志强耦合，不可直接照搬；
- 仍然保留一条**绝对红线**：任何情况下不得超过 §9 的硬限流上限
  （分位数预算是「更早收紧」，不是「允许更多」）。

### 13.3 立刻可以采纳的六条具体做法

| 做法 | 出处 | 落在本方案哪里 |
|---|---|---|
| **「绝不替他人发言」写成硬约束** | openclaw#121914：一个关掉 `requireMention` 的 agent 从主动评论**升级到替其他参与者发言，被运营方封禁**（它上下文里一直有「先旁观」的指令） | §9 风险表新增一行；criteria 里明确禁止 |
| **未回应计数做「没人理我就停」保险**（会话级：任何用户发言立即归零，累计 N 次暂停主动发言，群默认 2） | astrbot 主动聊天 | §3.1 的 `Topic.botSpeaks` 旁并列一个 `unansweredStreak` |
| **两个保险禁止「纯沉默触发」**（① 无新消息直接不允许触发；② 空档折算封顶 `阈值-1`） | MaiBot（注释原文「杜绝纯靠沉默累积反复唤醒回复」） | §3.2 台账探针：**探针只在有新消息时才有意义**，禁止仅因时间流逝而发言 |
| **仲裁拒绝也要落标记**（`mark_skipped`），避免反复撞同一堵墙 | np `pending_topics` | §3.2 新增状态 `silenced`（已评估但被否，不再重探） |
| **回复去抖合并**：判定为「在跟 bot 说话」后先等 ~1.5s，期间有新消息就合并成一次回复 | bl-chat `replyDebounceMs` | §7 之外的新增项：**S2 一并做**（现在的静默去抖 `20s` 是会话级，不是「连发合并」） |
| **异常一律不发言**：列出全部降级路径，原则是「不会让机器人哑掉、刷屏或抛异常」 | JEV 的十种 `decided=False` | 与现有 fail-closed 一致；在 §9 补「降级路径清单」测试 |

另外两条值得吸收但**不要照抄参数**的做法：

- **本地 logistic/规则打分当廉价门**（MaiBot 8 特征纯本地零 API 成本，
  最重的一项是 `recent_self_ratio=+2.65`）。⚠️ 这一项是**自激励风险**
  （bot 刚说过话 → 概率升高 → 更可能再说 → 占比更高）；若要抄这个结构，
  必须同时抄它的**记账 + 目标数封顶**对冲，或把该特征去掉/反号。
- **可调阈值与发言位置**（Koala II：把「0–100 分 + 固定阈值」改成
  用户可随时调的 high=90/medium=75/low=50 三档；并暴露「在频道还是在线程里发言」）。
  这是 §11 之外的**第六个设计轴：谁有权调阈值**（见 §14 开放问题）。

### 13.5 两个被高估的参考对象（避免误引）

- **KouriChat 的主动介入在当前代码里已不存在**：main 分支 82 个文件里正则搜
  `proactiv|schedul|task|timer|cron` 零命中；README 首行即「禁止接入微信、QQ 等
  腾讯系软件」。残留于归档分支的是 `AutoTasker` + `tasks.json` 发**固定字符串**，
  没有任何「要不要说话」的判断。
- **koishi-plugin-dialogue 不是主动介入系统**：它是教学向的规则问答库 +
  S/A 双概率。但其中有个**零成本实现场景 1 的技巧**值得记住：
  称呼被触发后「该会话的短时间内的提问取 S、A 两个概率的**最大值**」——
  对应我们「@ 之后同一话题的追问不该再要求 @」，与 `40-promotion-window`
  同源，也印证了「把话拆开说」是真实用户行为。
- 两处需要**降级参考**的具体实现：JEV 的判定整体依赖私有协议的外部决策服务
  （多一个强联网依赖、逻辑锁死在别人的模型里）；bl-chat 的 `forceContinue`
  路径**直接跳过 `applyRateLimitGuard()`**（源码注释自陈「跳过上限检查」），
  导致「10 分钟 8 条」这条最终防线对高频 @ 的群失效——**不要抄这个后门**。

### 13.6 ⚠️ 一个可能推翻全部预算设计的前置事实（需业务方确认）

调研查到[腾讯官方文档](https://github.com/tencent-connect/bot-docs/blob/master/docs/develop/api-v2/server-inter/message/send-receive/send.md)原文：**主动推送能力已于 2025-04-21 起不再提供**；
群聊主动消息**每月 4 条**（超额发送失败）；被动消息有效时间 5 分钟 / 最多回复 5 次；
且用户可以自行关闭接收主动消息（**关闭后主动消息一律失败**，代码侧不可知）。

对本方案的影响：

- 本方案的落点是**社区协议通道（OneBot / NapCat）**——P0 方案 §6.1 已定
  「本期仅接 OneBot，官方通道只留接缝」，审计也确认官方侧的
  `GROUP_MESSAGE_CREATE` 至今按触发消息处理（这是 P0 要修的隐患）。因此
  **C/D 两节的「每分钟 / 每话题」预算口径成立**，但只对 OneBot 成立；
- 一旦要走官方通道，**场景 3 与场景 5 几乎无法作为独立发言实现**
  （每月 4 条额度下，主动发言只能留给极少数最高价值情形），本方案的
  「按场景排优先级」会退化成「每月 4 次的稀缺额度调度」；
- 结论：**先确认通道再动预算层的参数**（见 §14 开放问题第 1 条）。
