# ADR-012：任务衔接基线的真实模型验证

状态：接受；日期：2026-11-08。

## 决策与内部契约

既有 L13/L14/L18 继续验证进度查询、新短问与追加条件。新增独立 live 组“真实任务衔接”：LC01 排队时沿用原任务实际产生的 UUID，LC02 执行完成但结果仍 pending 时的进度查询，LC03 原结果投递失败后的进度查询。进入完整 live 集，可单独选择；C01–C10 离线基准不改写。

所有回答由真实 DSH 产生。仅使用 Harness 的可释放 prompt 闸门安排原慢执行与新输入的先后，使用内存连接器的断连/发送失败制造投递事实，不写入 Task 或 MessageQueue 状态、不注入模拟模型回复。原任务被要求通过工具产生一次 UUID，后续输入仅复述已有编号；LC01 检查原任务结果在 B 准入后形成、实际派发 View 含该结果、B 沿用编号且没有再次调用业务工具。

RuntimeEvidence 增加实际 prompt 派发时间、工具名和独立 SessionContextView 块，只记录可见结果/上下文和元数据，不保留思考正文或业务工具参数。Harness 的 beforeRuntimePrompt 闸门在记录派发证据前等待，关闭时释放。

报告及裁判输入增加 deliveryEvidence：目标 Task、调用者 Task、采样时刻、执行状态及原始正文投递记录。LC02 在 B 实际查询和生成答复期间保持断连，采样确认 A completed/pending，再恢复出口交付 A 与 B；裁判按生成/查询时刻的证据评测，后续恢复送达不能替代当时缺失的证据。LC03 的失败记录保留，后续唤醒不得重试 A 正文。

新增场景具有 requiredAssertions，既有全局终态、重复平台尝试与关闭释放检查继续执行。场景前提缺失或证据不足不能标通过。校准与业务报告分轮保存，真实模型未遵循预期时如实失败，不改写回复或重判历史报告。

## 验证

先运行真实裁判校准和既有 L13/L14/L18 联合单样本；新场景通过注入 DSH 的离线流程检查后再运行真实模型。最后对既有与新增场景执行三次严格回归。离线、真实模型、真实 WebSocket 结果分别记录，真实模型验证仍使用内存 QQ 出口。
