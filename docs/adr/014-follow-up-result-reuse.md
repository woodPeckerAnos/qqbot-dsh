# ADR-014：普通关联追问必须完成当前结果复述

状态：接受；日期：2026-11-08。

## 问题与证据

ADR-013 的首轮六场景单次验收全部通过，但后续三次严格回归的 LC01 第一次失败：原任务恰好一次 bash 产生 UUID，派发给 B 的 View 含原 completed/sent 正文，B 快答仅承诺等待编号，B 慢模型却直接返回 NO_REPLY。existing-uuid-reused 必需断言拒绝通过，独立裁判的 pass 不能替代该断言；原报告不改写。

慢 lane 的“只交付新增信息，不复述已送达答案”和 profile 的“只交付新增部分”未在每处明确同 Task 范围，容易将其他 Task 已送达结果当作当前追问已经完成。

## 决策与生产契约

无增量静默以同 Task 快 lane 的实际成功送达正文为比较基准。当前输入明确要求引用或复述旧结果时，可以从只读 View 使用旧 Task 的可核对正文，必须在当前 Task 的答复中给出所需内容或明确引用；仅告知等待、稍后交付的快答没有满足本次请求，旧 Task 已送达不能替代这次答复。相同已有信息的明确复述不触发重新执行旧业务或生成旧附件。

runner、SessionContextView 渲染说明和默认 DSH profile 一致表达该范围。当前 Task 快答已完整回答时仍可 no-increment；纯进度 progressOnly 的慢 lane 仍由 scheduler 预计算静默，不创建 runtime。失败、截断、投递未知、资料不足及原任务 pending/sending 的边界保持既有契约，不推断遗漏内容，不声称未核对的送达。

不新增生产接口、状态、配置或持久化字段。SessionActor、TaskLifeCycleManager、MessageQueue 的写入所有权保持不变。

## benchmark 请求边界

同轮 LC02 三次运行断言通过，但裁判均达到 180 秒请求时限。新的裁判请求仅投影实际查询中的 Task 身份、状态、lane 结果和时间，移除不参与语义判分的 trace/execution 标识；完整原始查询结果仍保存在 RunRecord，不改变真实执行证据。UUID 工具来源只采集可见工具输出的 receipt 标记，不把 Task/trace 标识当作业务编号。

下一轮使用独立的 300 秒裁判配置并写入报告指纹；评分 v6、校准 v3、失败和未定门禁及禁止自动重试保持不变。旧超时不改判，不以增加时限冒充语义通过。

## 验证与发布

保留本轮完整失败报告，添加“B 只收到承接且慢 lane 静默”的离线反例；即使裁判回答 pass，必需断言和严格门禁仍失败。重新运行 session/协作相关回归、完整检查及 C01–C10 固定基线比较，再在新目录执行六场景单次与三次真实模型验收，不拼接旧通过样本。裁判 v6 和校准 v3 不改写。

最终验证见 [Phase 1 验收](../SESSION-CONTEXT-ACCEPTANCE.md)：后续 ADR-015/016 完成传输与进度措辞修正后，完整检查通过 1371 项离线测试与 39 个冒烟，固定基线比较 10/10；新的真实校准 14/14、六场景各三次运行与语义均 18/18，资源全部为零。LC01 三次均复述同一实际工具编号且没有重执行业务；历次漏答、超时与严重判定保留原报告。
