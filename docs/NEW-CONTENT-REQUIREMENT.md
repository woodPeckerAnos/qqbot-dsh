# 原始需求

（维护者原话，逐字保留）

> 第二个 topic-spent 指标太笨了，应该处理为新内容比例，新内容达到一定比例则允许发出

（前置讨论的结论，同样逐字保留其口径）

> 真正要度量的是「**决策状态**有没有变」

# 需求描述

## 问题：`topic-spent` 是"计数近似语义"

现状（一周灰度实测）：模型判"该说"550 次，其中 **494 次**被"本话题已介入过"否掉，
只有 56 次走到 `wouldSend`。

它的口径有两个毛病：

1. **长话题永久禁言**：`botSpeaksInWindow` 只在**活动窗口翻篇**时归零（静默 > 10 分钟），
   而人类消息只是把窗口续命、**不**清零。于是话题越热、越持续，bot 越是被自己的
   第一次发言永久禁言——一个聊了一下午的话题，全程只能说一句；
2. **它拦掉的未必是重复**：494 次里有多少是"真的没新东西"、多少是"有新东西但不让说"，
   现在无从分辨。而它想表达的其实只有一件事：**别把已经说过的话再说一遍**。

## 为什么不能用"词汇新词率"当这个指标（已实测否掉）

拿 8 个典型中文群聊场景实测（bigram 新词率 = 相对锚点的未出现双字组占比）：

| 场景 | bigram 新词率 | 该不该说 |
|---|---|---|
| B 有人答了（问题被解决） | **1.000** | ❌ 不该 |
| F 情绪与附和（"哈哈哈确实""同意""+1"） | **1.000** | ❌ 不该 |
| H 长话题但只重复既有信息 | 0.308 | ❌ 不该 |
| C 出现了新问题 | 1.000 | ✅ 该 |
| G 可确证的事实性错误 | 0.923 | ✅ 该 |

**结论：词汇新词率与"该不该说"不相关**——F（三句纯附和）拿了最高分，因为
"哈哈哈""同意""+1"这些词此前没出现过。中文短句 + 双字切分会让任何新措辞都拿高分，
于是最坏效果是**越水越容易触发**。

同理单看"新消息数"也不行：H 有 5 条新消息（最高）却全是重复既有信息。

## 正确的度量对象：会改变判定结果的事

按这个口径重看同一批场景，**8 个里 6 个的状态变化是本地可判的**：

| 场景 | 什么状态变了 | 能否本地判 |
|---|---|---|
| B 有人答了 | 挂起问题 → 已解决 | ✅ |
| C 出现新问题 | 台账 +1 条新条目 | ✅ |
| D 话题转移 | 活动窗口重开 → 旧话题的"说过没"清零 | ✅ |
| E 同话题深入 | 既有问题仍挂着 + 有他人尝试 | ✅ |
| A 反复抱怨 | 无新问题、无他人尝试 | ✅ |
| F 情绪附和 | 无问句、无主张、无人在做事 | ✅ |
| H 重复既有信息 | 同上 | ✅ |
| G 事实性错误 | 出现可确证主张的**形态** | ✅（形态可判，真假归判据） |

初稿的结论是"只有事实性错误必须靠 LLM"。**补上 `correctionClaim` 信号后，
8 个场景全部可以本地判**（它只识别**形态**、不判真假，见「# 判定」的验算表）。
因此本需求可以覆盖全部 8 个场景，而语义增量（精确判断"有没有真信息增量"）
降级为二期、仅在数据证明必要时才做。

# 判定

## 一、本地信号集（信号 = 会改变判定结果的事）

**解锁信号（3 个）**——每一个都代表"事情发生了变化"：

| 信号码 | 定义 | 判定方式 |
|---|---|---|
| `newQuestion` | 锚点之后**新登记**了挂起问题 | 台账：`askedAt > anchor` 的条目数 > 0 |
| `othersEngaged` | 锚点之后**别人在做事**，且满足其一：① 有人在挂起问题上发过言（尝试答但未收口，`senderId ≠ askerId`）；② 出现了新的发言人**且**锚点后的人类消息 ≥ `newContentMinMessages` | 台账发言时间戳；参与人集合按时间戳过滤 |
| `correctionClaim` | 锚点之后出现了**可确证主张**的形态（数字 / 版本号 / 单位 / 报错串 / 否定式断言） | 本地正则（**宁漏不误报**：它只是"值得重判"的信号，真假仍归判据） |

**终止信号（1 个）**——出现它就意味着"没什么可补的了"：

| 信号码 | 定义 | 判定方式 |
|---|---|---|
| `answerArrived` | 锚点之后有挂起问题被关闭（被答 / 被静默 / 过期） | 台账关闭事件的时间戳 > anchor |

**窗口信号（1 个）**——它不参与计数，直接短路：

| 信号码 | 定义 | 判定方式 |
|---|---|---|
| `windowRolled` | 活动窗口已翻篇（静默超过窗口） | `topicId(now) === undefined`，或窗口起点 > anchor |

> ⚠️ **刻意不把"出现了新发言人"单独当解锁信号**（初稿曾如此，实测验算时发现漏洞）：
> F（"哈哈哈确实/同意/+1"，3 个新人）与 H（3 个新人重复既有信息）都会因此被放行。
> 把它并入 `othersEngaged` 之后，**"有新的人"与"有人在做事"是同一件事**——
> 而"有人在做这件事"才是真正的变化。代价是 E（多人深入讨论）仍能解锁
> （有 `attempted`），F/H 则退回判据拦截。

**锚点（anchor）三种取法，按用途选**：

| 锚点 | 取值 | 用途 |
|---|---|---|
| `lastEvaluationAt` | 该会话上次**进入判定**的时间 | 本地"要不要再评估一次"的门槛（wait 的闸 4 已用） |
| `lastBotSpokeAt` | bot 上次在该会话发言的时间 | **话题级**的"说过没"判断（替代 `topic-spent`） |
| `undefined` | 无锚点 | 视为"全新话题"，信号集直接用当前窗口全量 |

## 二、`topic-spent` 的替换规则（本需求的核心）

原规则：`botSpeaks(now) >= maxPerTopic` → 一律 `silent('topic-spent')`

```
新规则：先算信号集（锚点 = lastBotSpokeAt）
  ① windowRolled 为真                     → **允许**（话题已翻篇，等同新话题）
  ② 无锚点（bot 从未在此话题说过）        → 信号视为齐备 → **允许**
  ③ answerArrived 为真                    → **禁止**（这话题已经被解决了，没什么可补的）
  ④ 否则，解锁信号数 ≥ newContentMinSignals
     且人类消息数 ≥ newContentMinMessages  → **允许**
  ⑤ 否则                                  → silent('topic-spent')，并记录缺失的信号清单

判定顺序即优先级：**窗口翻篇 > 无锚点 > 已收口 > 信号够不够**。
```

注意：**允许 ≠ 一定发言**——真不真说仍由判据（`satisfied`）决定，之后还要过
硬限流（`rate-limit`）。本规则只解除"因重复而禁言"，不放宽频率。

## 三、对既有 8 个场景的验算（这条规则必须逐一成立）

| 场景 | 锚点后解锁信号 | 结果 | 对照"该不该说" |
|---|---|---|---|
| A 反复抱怨（2 条、2 人、1 个问句但已在锚点内） | 无（问句在锚点前，人也在锚点前） | **禁止** | ✅ 一致 |
| B 有人答了 | `answerArrived` | **禁止** | ✅ 一致 |
| C 出现新问题 | `newQuestion` | 允许 | ✅ 一致 |
| D 话题转移 | `windowRolled` | 允许 | ✅ 一致 |
| E 同话题深入（3 人 4 条，含"我不会啊"这类在问题上的发言） | `othersEngaged` | 允许 | ✅ 一致 |
| G 事实性错误（"文档写的是每分钟 600 次"） | `correctionClaim`（数字 + 否定式断言） | 允许 | ✅ 一致（**初稿判错，靠信号补回**） |
| F 情绪附和（"哈哈哈确实/同意/+1"） | 无（新人但无人"做事"、无问句、无主张） | **禁止** | ✅ 一致（**初稿会误放行，已修**） |
| H 重复既有信息（3 人 5 条） | 无（同上：有新人但没新事） | **禁止** | ✅ 一致（**初稿会误放行，已修**） |

**这条验算表是初稿的"捉虫器"**：第一版的信号集里"新发言人"是独立解锁信号，
于是 F 与 H 都被放行（两例的真实标签都是"不该说"）。把 `newSpeaker` 并入
`othersEngaged`、并补上 `correctionClaim` 之后，8 个场景**全部与标签一致**——
包括 G（初稿的已知缺口，被 `correctionClaim` 捞回）。

**仍然保留的诚实标注**：`correctionClaim` 用的是本地正则，它只能识别**形态**
（数字、版本号、报错串、否定式断言），识别不了真假。所以它带来的是**召回**
而不是**精度**：形如"不是 3 个是 5 个"的无害陈述也会解锁。这是可接受的——
解锁只意味着"值得重判一次"，真假由判据负责。

## 四、锚点必须存下来（否则语义层永远做不了）

bot 每次发言时，把**自己说的那句话**记进话题账本（`lastBotUtterance`）。

理由：语义增量（`novelty.vsLastBotUtterance`）必须与"bot 上次说的那句"比，
而不是与固定的"最近 N 条"比——否则话题长跑之后 bot 上次那句话会被挤出窗口，
参照点消失会导致增量虚高。本需求先把锚点存好，语义层才有可比的基准。

## 五、分母下限

只有 1 条新消息时算不出有意义的"变化"（可能就是一句"好的"）。因此：

- 人类消息数 < `newContentMinMessages`（默认 2）**且**没有任何解锁信号
  → **不解除禁言**；
- 反之，即使只有 1 条消息，只要它带来了 `newQuestion` / `othersEngaged` /
  `correctionClaim` 中任意一个，就解除。

这条的用意是**用信号补足样本量**，而不是要求"必须先攒够 N 条"。
`newQuestion` 与 `correctionClaim` 本质上都是**单条消息就能成立**的信号，
所以下限几乎不会误伤它们。

# 参数

| 名字 | 默认值 | 含义 |
|---|---|---|
| `newContentMinSignals` | `1` | 解除"本话题已说过"所需的最少本地信号数（硬上限 `3`） |
| `newContentMinMessages` | `2` | 锚点以来的人类消息条数下限（配合信号使用） |
| `semanticNoveltyMin` | `0.5` | 语义增量阈值；**本期不启用**，字段先留 |

`newContentMinSignals` 默认只要求 1 个信号，是刻意的保守选择：本地信号本身已经是
"决策状态变了"的证据，要求更多会让规则退化成另一个"计数阈值"。

# 验收标准

1. 无锚点（bot 在该话题从未发言）→ 判定**允许**，且计 `new_content_anchor_missing`；
2. `answerArrived` 为真 → 判定**禁止**（即使同时有 `newQuestion`）；
3. 有锚点且无 `answerArrived`，信号数 ≥ `newContentMinSignals` 且人类消息数
   ≥ `newContentMinMessages` → **允许**，计 `new_content_unlocked{signal}`；
4. 信号不足 → **禁止**，计 `new_content_locked`，并记录**缺失的是哪些信号**；
5. 只有 1 条新消息、但带 `newQuestion` → **允许**（信号补足样本量）；
6. 只有 1 条新消息、无任何信号 → **禁止**；
7. `windowRolled` 为真 → 视为全新话题，**允许**且不要求其它信号；
8. `newContentMinSignals` 配成 `5` → 按硬上限 `3` 处理并 warn（防止把规则改成"永不解除"）；
9. bot 每次发言后，`lastBotUtterance` 被写入话题账本，且内容为**该次发言的文本**；
9b. **"出现新发言人"单独不构成解锁**：只有新人、没有问句/尝试/主张时 → **禁止**
    （这是 F/H 两个反例的直接验收）；
10. 本规则**只**解除"因重复而禁言"：`rate-limit`（10 分钟 3 次 / 1 小时 8 次）
    的判定顺序与阈值**不变**；
11. 新信号与旧口径的对照数据可读：一周后 `new_content_unlocked` /
    `new_content_locked` 与 `satisfiedByScene` 的联合分布，能回答
    "解除禁言后有多少次真的走到了发言"；
12. `windowRolled` 的判定**先于** `answerArrived`（话题已翻篇时，旧问题是否收口
    不再影响判定）。

# 边界与反例

| 情形 | 处理 | 理由 |
|---|---|---|
| F 情绪附和（3 个新发言人） | **放行**，靠判据拦 | 本地只判"要不要重判"；"新的人进来了"确实是新信息 |
| H 长话题重复既有信息（3 人 5 条） | **放行**，靠判据拦 | 同上。**不假装本地能判语义重复** |
| G 事实性错误 | `correctionClaim` 解锁 | 只认形态：形如"不是 3 是 5"的无害陈述也会解锁——可接受，真假归判据 |
| 问题刚被回答，同时群里开了个新问题 | `answerArrived` 优先 → **禁止** | 旧话题已收口，新问题走它自己的评估路径 |
| bot 发言后没人理，群里只有 bot 自己的发言 | 无人类消息 → **禁止** | 与"没人理我就停"同向，不叠加新机制 |
| 锚点时间戳晚于缓冲里的所有消息（消息被淘汰） | 视为无锚点 → **允许** | 宁可多判一次，也不要因为"看不见"而永久禁言 |
| 同一秒内 bot 发言 + 人类消息（时间戳相等） | 以 `>` 严格比较 → 该消息**不算**新内容 | 避免"用同一条消息给自己解锁" |
| 活动窗口在锚点之前就已存在 | 正常算信号；`windowRolled=false` | 窗口语义不变，只是多了一层信号判断 |
| 每个信号都算了但都为假 | **禁止**，并记录缺失信号清单 | 这是 `topic-spent` 的**正当使用**（确实是重复） |

# 可观测性

| 计数 | 回答什么 | 期望形态 |
|---|---|---|
| `new_content_unlocked{signal}` | 是哪个信号解除了禁言 | 按信号分布 → **直接决定语义层值不值得做** |
| `new_content_locked` | 因重复被禁言 | 与改造前 494 次/周对照，看降了多少 |
| `new_content_anchor_missing` | 无锚点（全新话题） | 高说明多数介入发生在没有历史包袱的话题上 |
| `satisfiedByScene` × `new_content_*` 联合 | 解除禁言后真正发言的比例 | **这一项才是"新内容比例"好不好用的答案** |

**这一期的产出不是阈值调优，而是分布数据**：四个信号各自的命中率决定第二期
（语义增量）值不值得做。若 `newQuestion` 单独就覆盖了 70% 的放行，
那语义层可能根本不需要。

# 分期

| 期 | 内容 | 为什么这么排 |
|---|---|---|
| **一期（本需求）** | 本地信号集（3 解锁 + 1 终止 + 1 窗口）+ `topic-spent` 替换 + 锚点落库 | 全部本地可判、零 LLM 成本、纯确定性，且立刻修掉"长话题永久禁言"；8 个场景的验算全部与标签一致 |
| **二期（观察后定）** | 判据输出 `novelty` 字段（`vsLastBotUtterance` / `vsFullTranscript`）+ `semanticNoveltyMin` 生效 | 需要一期给出"信号命中率"才知道值不值得加；加它要改判据 prompt 并重新校准 |
| **三期（可选）** | 用 `novelty` 分数替换 `newContentMinSignals` 的粗判 | 只有当一期的信号分布证明"本地判不准"时才做 |

**不在本需求内**：改动判据文案（二期）、`topic-spent` 的硬限流阈值、wait 机制
（已单独立项，见 `WAIT-CONVERGENCE-REQUIREMENT.md`）。

# 与既有需求的关系

- **`WAIT-CONVERGENCE-REQUIREMENT.md`**：已实现（未提交）的 `hasNewContentSince()`
  是 `buffer.some(entry => entry.ts > since)`——**只回答"转录有没有新增消息"**，
  是 wait 的闸 4，与本需求的信号集**不重复**：前者回答"要不要重问"，后者回答
  "解不解禁"。两者共用 `anchor` 的概念，因此本需求的实现应复用同一个时间戳来源，
  不要再造一套。
- **架构文档 §3.0**（状态只按会话/话题/问题记账，永不按场景记账）：信号集挂在
  会话状态上，**不按场景分账**——同一条信号对多个场景同时可见。

# 背景与调研来源

- **触发数据**：一周灰度，`satisfiedByScene` 550 次、`topic-spent` 494 次、
  `wouldSend` 56 次（模型意图的 90% 被"每话题一次"拦掉）；
- **词汇新词率被否掉的依据**：本文件「# 需求描述」的 8 场景实测表（本地跑的一次性
  探索脚本，样本为典型中文群聊语句）；
- **"本地只判要不要重判，不判该不该说"**：与架构文档 §1.1 和生态调研的结论一致
  （JEV 用纯字符串包含做兴趣预筛、命中只作 hint 注入，不直接放行）；
- **`topic-spent` 的正当性保留一处**：边界表最后一行的"全假 → 禁止"——
  这是唯一真正"重复"的情形，也是这个机制不该被完全删掉的理由。
