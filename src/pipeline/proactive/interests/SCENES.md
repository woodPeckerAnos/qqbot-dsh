# 当前生效的主动介入场景（自然语言真相源）

> **这份文件是"bot 会主动说什么"的唯一人话版说明书。**
> 它面向三类读者：产品 / 运营（"它到底会在什么时候插话"）、排障者
> （"它刚才为什么说话"）、以及后续新增场景的 agent（先在这里写人话，再写代码）。
>
> **契约（由测试强制）**：`src/pipeline/proactive/contract.ts` 的 `SCENE_ORDER`
> 里出现的每个场景 id，都必须在本文件中有一节自然语言描述；
> 反之，本文件里写的场景若没有对应代码，就是"文档超期"。
> 校验见 `tests/scenes-layers.test.ts` 的「验收20」。
>
> 代码实现：`scene/collect.ts`（什么时候可能命中）→ `judge/judge.ts`（成立的判据）
> → `veto/veto.ts`（顺序与额度）；投递走 `deliver/speaker.ts`。
>
> **状态：已接入运行时（默认灰度观察）**。链路是
> 旁听消息 → `ProactiveWatcher` → 本地预筛 → 判定 → 否决 → `ProactiveSpeaker` → 适配器。
> 两个默认值决定了它当下的实际行为：
>   1. `proactive.enabled` 默认 **false**（不配就不主动开口）；
>   2. `proactive.dryRun` 默认 **true**——即使打开了总开关，它也只记录
>      "本应发言"（health 里的 `wouldSend`），不会真的说话。
> 也就是说：**要让 bot 真的主动开口，需要同时配置 `enabled: true` +
> `dryRun: false` + `BOT_LISTEN_GROUPS`**。排障见
> [docs/RUNBOOK.md](../../../../docs/RUNBOOK.md) §4.5。
>
> 已知的简化（刻意，不是未完成）：场景 1/2/5 的"话题"用**活动窗口**近似
> （静默超过 10 分钟算翻篇），不做话题聚簇；架构讨论见
> [docs/PROACTIVE-INTERVENTION-ARCH.md](../../../../docs/PROACTIVE-INTERVENTION-ARCH.md) §3。
>
> **放行闸门是"话题 session"**（详见
> [docs/TOPIC-SESSION-REQUIREMENT.md](../../../../docs/TOPIC-SESSION-REQUIREMENT.md)）：
> 判定判"值得"时才开一次会话，里面最多说 `sessionBudget` 句（默认 2），
> 说完/模型说收口/静默 10 分钟即关。它**取代了旧的"每话题一次"**，
> 代价是明确接受的覆盖率损失——不做本地话题识别。

## 一句话总览

bot 平时在群里**旁听**，只有在下面五类情形下才可能主动开口；
五类同时成立时，**按本文的排列顺序取第一个**（4 → 1 → 3 → 2 → 5）。

| 顺序 | 场景 | 什么情况下会出现 | 命中后 bot 会做什么 |
|---|---|---|---|
| 1 | **4 · 指代** | 有人没 @ 它，但话其实是说给它听的 | 直接回答 / 确认能力 / 接住请求 |
| 2 | **1 · 续聊追问** | 它刚参与过这个话题，有人接着追问 | 把没讲清的讲清、把没答的答上 |
| 3 | **3 · 无人应答** | 群里有个具体问题，问出来一段时间没人理 | 主动把那题接过来答 |
| 4 | **2 · 持续讨论** | 几个人来回讨论一个话题，它没参与 | 只在能给出"信息增量"时补一句 |
| 5 | **5 · 兴趣 / 性格话题** | 讨论命中了它的兴趣池条目 | 只补一句**能立刻用**的结果 |

**顺序的含义是"谁先被听到"，不是"谁有资格说"。** 顺序靠前的场景不会因此
更容易通过限流——所有场景共用同一套防刷屏闸门（见本文末「全局闸门」）。

## 场景 4 · 指代（优先级最高）

**人话**：群里有人没 @ 机器人，但说了句其实是在跟机器人说的话——
可能叫了它的名字，也可能只是说了"机器人/助手"加上一个请求。

**什么时候算**：

- 有人喊它的名字（配置的别名，如"小助手"）并说了事；
- 或者用了"机器人""助手"这类泛称，**同时**带着请求的意思
  （"帮我""能不能""试一下""在吗"……）。

**什么时候不算**（这条最容易误伤，所以收紧）：

- **只是在议论它**——"这机器人是不是坏了""要不要换个机器人"，
  这是在跟群友聊天，不是在跟它说话；
- 有人 **@ 了别人**；
- 只是提到它的名字，但话题跟它没关系。

**典型对话**

```
张三：小助手你有空吗，帮我看下这个报错        ← 命中（叫了名字 + 有事）
李四：它是不是又卡住了，怎么不回                ← 不命中（在议论它）
王五：机器人能帮我把这个表格转成 csv 吗          ← 命中（泛称 + 请求）
```

## 场景 1 · 续聊追问（优先级第二）

**人话**：它刚在某个话题里说过话，紧接着有人就**同一个话题**继续追问或延伸。

**什么时候算**：追问的疑问点**还没有被任何人解决**（包括提问者自己
后来想明白了、或群里别人已经答了）。

**什么时候不算**：只是继续闲聊；话题已经转走了；群友已经回答得很完整。

**同时管两件事**：如果追问里包含**可确证的事实性错误**（数字、单位、
代码报错、常识），它只纠这种；观点、偏好、预测、价值判断一律不纠，
不确定也不纠——"温和地补充一点"正是最招人烦的那种行为。

**典型对话**

```
bot ：这个报错是因为 requests 没装，先 pip install requests
张三：那如果是公司内网装不了呢                    ← 命中（同一话题继续追问）
李四：谢了，我先试试                              ← 不命中（无追问点）
```

## 场景 3 · 无人应答（优先级第三）

**人话**：群里有人问了一个**具体问题**，过了一段时间**没人回答**，它就把这题接过来。

**节奏（特意留出让人先答的时间）**：

1. 问题出现 → 先挂 **90 秒**，什么都不做（群里可能正在打字）；
2. 90 秒仍无人应答 → 交给判定，看这题是否在它能力范围内；
3. 判定认为"先别说"时，它必须说清是**哪一种**先别说（`waitReason` 三态），
   而每种理由的唤醒责任人完全不同：

| `waitReason` | 它想说的 | 谁负责下次唤醒 | 会不会再花一次判定 |
|---|---|---|---|
| `yielding` | 有人在答（正在打字、刚接话） | 本机制：45 秒后重查一次 | 会（**只此一次**） |
| `not-yet` | 还没到时候（问题太新、话题刚起） | 上面第 1 步的 90 秒探针 | 不会（按静默处理） |
| `watching` | 刚说完，看反应 | 群里下一条消息自然唤醒 | 不会（按静默处理） |

**"再等等"的硬约束**（写在代码里，不是写在提示词里的请求）：

- `yielding` **必须**报出它在等哪一个挂起问题（`evidence` 里回抄 `q:<id>`）；
  报不出有效 id 就按静默处理，**不猜对象**、也不退化回"无限等"；
- 同一个问题**最多让路一次**（`proactive.maxWaitPerItem`，硬上限 3），
  且这次重查只有一次机会——重查之后无论判成什么都不再唤醒第二次；
- 重查前先做两道**本地**检查：对象还在吗（问题已被答/过期/话题翻篇 → 作废）、
  转录自上次判定以来有新增吗（群里一直安静 → 不花这次判定）；
- 问题一旦被回答，等待**当场作废**，而不是等定时器到点才发现。

**什么时候算**：问题确实还没被回答 + 这题它能答 + 已经安静够久（越久越值得答）。

**什么时候不算**：问题已经被答了；问题是指名问某个人的；属于私人或情绪话题；
超出它的能力范围。

**典型对话**

```
张三：有没有人知道这个接口的分页参数怎么传？      ← 静默 90 秒无人答 → 命中
李四：我看看                                        ← 90 秒内有人接话 → 不命中
张三：有没有人知道这个接口的分页参数怎么传？      ← 判定说"李四在答" → 让路 45 秒
李四：（45 秒里一直没说话）                          ← 重查时转录无新增 → 不花判定，作废
```

## 场景 2 · 持续讨论（优先级第四，最需克制）

**人话**：几个人围绕一个话题来回讨论，它一直没参与，
但讨论里出现了**它能提供价值的地方**。

**什么时候算**（三个条件满足一个，且必须能带来**新的信息**）：

1. 讨论里出现了它擅长的能力需求——查资料、跑代码脚本、数据与图表、
   文件生成与转换、多步任务；
2. 讨论里有个问题没人能答，而它能答；
3. 有人说了可确证的事实性错误。

**什么时候不算**：纯观点碰撞、情绪与闲聊、玩笑；群友已经说清楚了；
它只能复述别人说过的东西（没有信息增量）。

**这一类是五类里最容易招人反感的**（生态调研里，主动版 AI 被 72% 用户
评为"像不肯给别人留空间的说教学生"）。所以门槛高、宁缺勿滥。

**典型对话**

```
张三：这个月的数据我手工算了一晚上
李四：Excel 拉个透视表不就行了
张三：我不会啊
      ← 命中（出现了它的能力域：数据处理与图表，且讨论停在"没人动手"处）
```

## 场景 5 · 兴趣 / 性格话题（优先级最低，门槛最高）

**人话**：讨论命中了它**兴趣池**里的条目（配置在人审过的兴趣清单里），
并且这个话题正好**卡在没人能给结论**的地方。

**什么时候算**：话题停在"没有结论"或"没人动手"处，
而它能补一句**可以立刻使用**的结果——一条结论、一段代码、一张图、一个文件。

**什么时候不算**：话题还在推进；已经有群友给了同等或更好的答案；
它只能贡献感想或附和；这个话题里它已经就这条兴趣说过一次了。

**典型对话**

```
张三：这个折线图怎么画都看不出趋势
李四：要不换个图？
      ← 命中（兴趣池含"数据可视化" + 话题停在没人动手处 → 直接给一张图）
张三：今天天气真好啊                              ← 不命中（没命中兴趣池）
```

### 怎么给这个场景加兴趣条目

> ⚠️ **这个形态是过渡态**：后续迭代会加入 **role-play（角色扮演）** 环节，
> 兴趣池将由 role-play **动态设定**。届时"手写 interests.yml"会退化成
> 可选的人审 / 兜底手段，而**场景 5 的判据与门槛不变**。
> 所以下面这套"加条目"的方法在 role-play 上线后依然成立，
> 只是条目的**来源**多了一条（甚至主要来自 role-play）。

兴趣池是一份**人审过的清单文件**（关键词匹配在本地完成、零成本；命中之后
才进判定）。三步：

1. 把样例复制成配置文件：

   ```bash
   cp src/pipeline/proactive/interests/interests.yml.example interests.yml
   ```

2. 按下面的字段加条目（完整注释见
   [interests.yml.example](interests.yml.example)）：

   ```yaml
   interests:
     - id: plotting                 # 必填，文件内唯一，英文小写
       topic: 数据可视化 / 画图      # 必填，一句话说明"这是聊什么"（进 prompt）
       keywords: [画图, 折线图, matplotlib]   # 必填，字符串包含匹配，至少两个词
       why: 我有 matplotlib 与文件出站能力，可以直接给图   # 选填（进 prompt）
       note: 只给结论，不要先讲原理                        # 选填（进 prompt）
   ```

3. 填错不用猜：**文件不存在 = 兴趣池为空（合法，场景 5 不触发）**；
   **文件存在但格式错 = 启动期报错**，并会指出是第几条、哪个字段
   （id 重复、关键词少于 2 字、超过 20 条都会拦）。

几条实践经验：

- **关键词宁准勿宽**：太短的词会误命中（"图"会命中"图书馆"），
  所以校验直接拒绝单字关键词；
- **关键词越准越省钱**：命中才进判定，命中越少白花的调用越少；
- **每话题最多说几次不在这里**——那是话题 session 的发言预算
  （`qqbot.yml` 的 `proactive.sessionBudget`，对所有场景统一），
  写进兴趣池会形成两套账；
- **临时停用**：`qqbot.yml` 的 `proactive.interestsEnabled: false` 或整份停用
  `proactive.enabled: false`。

**怎么改、改了怎么生效**：改 `interests.yml` 后**需要重启进程**（兴趣池在启动时读一次；
运行期热更新是 role-play 迭代的事，接缝已留在 `replaceHotWords` 之外的
`InterestPool.replaceEntries()`）。

**给后续做 role-play 的人（也是给 agent 的约定）**：

- 兴趣池的**上游是可替换的**：`InterestPool` 只管"校验形状 + 本地匹配 +
  喂给判定"，不关心条目从哪来。role-play 要做的只是产出 `InterestEntry[]`
  并调 `replaceEntries()`（原地替换，调用方引用继续有效）；
- **动态 ≠ 免检**：role-play 生成的条目仍要过同一套校验
  （id 唯一、关键词 ≥2 字、条数上限）——否则"动态"会变成"不可解释"；
- **不要把"兴趣来自 interests.yml"写进 `scene/` `judge/` `veto/` 的任何假设**：
  那一天这三层不该有任何改动。

## 全局闸门（不属于任何场景，对所有场景一律生效）

1. **没人理我就停**：连续 2 次介入后群里毫无回应 → **全体静默**
   （任何用户发言立即归零，重新计数）。这条在判定之前就生效，不浪费判定成本。
2. **话题 session（本需求的核心闸门）**：判定判"值得"时才**开一个话题会话**，
   在它里面才允许主动开口；一个话题最多说 `sessionBudget` 句（默认 2，硬上限 5）。
   说满之后**会话不关，只是这个话题里不再开口**（预算不该驱动会话的生死）：
   要重新开口，必须由**话题**驱动——模型说"换话题了"（`session: 'new-topic'`，
   旧会话让位、预算重置），或者会话收口 / 静默超时才结束。会话的关闭只有三种原因：
   **模型说这个话题收口了**（`close`）、**模型说换话题了**（`new-topic`）、
   或者**静默超过 `sessionIdleMs`**（默认 10 分钟，锚点是 bot 自己上次发言的时刻）。
   同一会话内两次发言至少隔 `sessionMinGapMs`（默认 45 秒），没到就闭嘴
   ——但**不消耗预算**（预算是"说了几句"的账，不是"想过几次"的账）。
   **这条闸门取代了旧的"每话题一次"**：话题是 LLM 之后才明确的东西，本地按
   活动窗口数"这个话题说没说过"记不准；代价是**放弃介入话题的覆盖率**
   （不是所有值得聊的话题都会介入，话题换了也可能漏一轮），这是明确接受的取舍。
3. **发言后高敏期**：刚说完话的一段时间内，进入话题的每条消息都会被重新
   审视（而不是"说过一次就闭嘴"），但如果群里没人接它的话，会自动降级收敛。
4. **硬限流**：每群 10 分钟最多 3 次、1 小时最多 8 次主动发言；**不排队**，
   超限即放弃（话题已经翻篇，补发没有意义）。它**先于**话题 session 闸门——
   会话预算不会把 10 分钟 3 次的上限放宽。
5. **夜间静默**：配置的夜间时段内不主动发言。
6. **平台能力**：社区协议通道（OneBot）可以直接发；**官方通道目前不支持主动
   发言**（官方主动推送 2025-04-21 起停用，群聊主动消息每月 4 条，用户还可自行
   关闭接收）——在官方通道上，以上场景全部"判定照跑、发言降级"，
   这是预期行为而不是故障（见 [README.md](../README.md) §1）。

## 明确不说的话（硬红线）

- **不替他人发言**：不替群友下结论、不代言、不"代表大家"。
  （生态里真实发生过：一个关掉"必须 @"限制的 agent 从主动评论升级到替别人
  发言，被运营方封禁。）
- 不评论人、不给群友贴标签、不参与争吵；
- 不把"情绪、偏好、预测"当成错误去纠正；
- 在没有信息增量时不说"我同意""确实""哈哈"这类凑数的话。

## 后续新增场景：先在这里写人话，再写代码

**约定（也是契约测试的校验对象）**：任何新增的主动介入场景，
必须**先在本文档里新增一节自然语言描述**，说清四件事：

1. **什么情况下出现**（触发时机，人话）；
2. **什么算命中、什么不算命中**（判据，人话，含反例）；
3. **至少一个典型对话例子**（用群里真实说话的样子，不要用抽象描述）；
4. **误报的代价是什么**（这条决定它的优先级与门槛高低）。

若新场景需要自己的配置面（像场景 5 的兴趣池那样），同样先在本文档写清
"维护者怎么加条目、写错了会怎样"，再去做配置文件与校验。

然后再去改三处代码（缺一处契约测试就红）：

| 步骤 | 文件 | 改什么 |
|---|---|---|
| 1 | `contract.ts` | `SceneId` 加新 id；在 `SCENE_ORDER` 里定位置（顺序是产品决策） |
| 2 | `collect.ts` | `SCENE_DEFINITIONS` 加一条（`name` / `triggers` / `precheck`） |
| 3 | `judge.ts` | 加判据文案并登记进 `CRITERIA_TEXT` |

**验证**：`npx vitest run tests/scenes-layers.test.ts`（19 条三层契约用例 +
「验收20」的文档一致性校验）。

> 备注：`SCENE_ORDER` 的顺序与本文的章节顺序必须一致——
> 这是"先写人话"的具体含义：先决定它在业务上排第几，再去改代码里的下标。
